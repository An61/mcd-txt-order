# 把麦当劳 MCP 接进微信：只有真跑一遍才会踩到的坑

> 本文不是 README 的复述，而是把开发 `mcd-txt-order` 过程中**用真实调用试出来的东西**记下来。
> 官方文档给了工具清单，但工具之间的顺序依赖、字段的真实单位、哪些参数其实不起作用——
> 这些只有把请求真的发出去才知道。
>
> 如果你也在做 MCP 集成，第三节的五条和第六节的取舍大概能帮你省下几天。

---

## 一、先看清你拿到的是什么

麦当劳 MCP 的接入很干净：一个 Streamable HTTP 端点 `https://mcp.mcd.cn`，Header 带 `Bearer <token>`。
但有两件事和文档写的不一样：

**1. 工具数量对不上。** 文档写 28 个，实际握手拿到 **35 个**。服务端在迭代，别把文档当契约，
把 `tools/list` 当契约。

**2. 没有 Token 就不是"受限"，是完全不通。** 带空 Token 是 403，不带是 401，
连 `tools/list` 都拿不到。这意味着：**字段解析必须写成容忍式归一化**，因为你没法在拿到凭据前
把结构摸清，而拿到凭据后你已经在线上了。

响应信封是统一的 `{success, code, message, datetime, traceId, data}`，
工具同时返回 `structuredContent`（结构化）和 `content[].text`（Markdown 给人看）。
**永远优先取 `structuredContent`**，Markdown 那一份是给人类读的，不是给程序解析的。

## 二、下单链路是锁死的，不能跳步

这是整个集成里最重要的一张图：

```
query-nearby-stores   拿 storeCode
        ↓
query-meals           拿菜单（注意要带 reservationDate）
        ↓
query-meal-detail     只有做特制时才需要
        ↓
calculate-price       ★ 唯一能拿到 takeWayCode 的地方
        ↓
   用户二次确认
        ↓
create-order
```

**`takeWayCode` 只能从 `calculate-price` 的返回里取，没有第二个来源。**
我一开始以为这是个可以枚举的常量（堂食/外带），试过直接构造——下单直接失败。
所以 `create-order` 之前必须走完 `calculate-price`，**这一步不是优化项，是硬依赖**。

代码里的处理是：取不到就中止并返回人话错误，**绝不猜一个值继续**。
宁可让用户重发一次，也不要拿着猜的参数去创建真实订单。

同样的还有场景映射，错一个全链路失败：

| 场景 | beType | orderType | 额外必填 |
|---|---|---|---|
| 到店自提 | 1 | 1 | 无 beCode |
| 得来速 | 5 | 1 | **必须传 beCode** |
| 麦乐送 | 2 | 2 | 需 addressId |
| 企业团餐 | 6 | 2 | — |

## 三、五个文档没写的坑

### 坑 1：官方「收藏餐厅」这条路走不通

用户想要"预置喜爱的门店"，第一反应是用官方收藏能力（`searchType=1`）。实测：

```json
{ "success": false, "code": 600050,
  "message": "收藏餐厅列表为空，请您提供城市+关键词进行搜索" }
```

而且**这个状态下 keyword 会被完全忽略**——传了和没传一样。
所以收藏路径不但可能为空，还**不支持关键词过滤**。

**解法**：空即回退到 `searchType=2`，且必须 `city + keyword` 同时给（只给其一报 600058）。
官方收藏是"优化路径"，本地别名配置才是"保底路径"，两者都要有。

### 坑 2：keyword 其实不过滤

搜「星河」，服务端返回了 5 家门店：星河、云杉路、晨曦、湖畔、松风。

**keyword 没有做名称匹配，它只是圈了一个地理范围。**
所以正确做法是"别名在本地、名单在云端"：把候选池取回来，**本地再匹配一次**。

这个坑很隐蔽——如果你只店里只收藏了一家，测试永远是过的，直到某个用户附近有同名商圈。

### 坑 3：`reservationDate` 是会话上下文，不是单次参数

`query-meals` 带 `reservationDate="2026-10-10 12:00"` 能拿到午餐菜单。
但后续 `query-meal-detail` / `calculate-price` 如果不补**同一个值**，会报：

- `60001 未匹配到商品`
- `60006 商品已售罄或不可售`

补上立刻成功。**它不是可选参数，是贯穿整条链路的上下文。**
工程上的处理：把它放进会话状态里，每次调用自动带上，不要让调用方各自记着传。

### 坑 4：菜单是两份数据，要 join

`data.categories[]` 长这样：

```json
{ "name": "汉堡", "meals": [ { "code": "1100", "tags": [] } ] }
```

**只有裸 code，没有名字和价格。** 名称和价格在另一个 `data.meals` 字典里：

```json
"meals": { "1100": { "name": "巨无霸", "currentPrice": "26.5", ... } }
```

只遍历 categories 的话，你会拿到一堆没有名字的商品。必须先字典补全。

### 坑 5：金额有两套单位

- 菜单的 `currentPrice`：字符串，**元**（`"26.5"`）
- `calculate-price` 的 `price / subtotal / discount`：**整数，分**（`2650`）

混用会直接算错钱，而且是那种"看起来对"的错——26.5 和 2650 在日志里都挺合理。

**解法不是"记得换算"，是让类型系统替你记。** 领域模型里金额一律用「分」整数，
字段名统一带 `Cents` 后缀（`priceCents` / `discountCents`），
两个换算函数分别命名为 `yuanToCents` / `centsToYuan`，且**只在边界处调用**。
写代码时看到 `price` 不带 `Cents` 就知道它还没过边界。

## 四、特制：无法从服务端验证的那一步

"不要酸黄瓜"这类特制，`modification.values[].code` **只能从 `query-meal-detail` 取**，不能凭空构造。
巨无霸的酸黄瓜实测 `code=100202`，`selectedKey="0-1"` / `unselectedKey="0-0"`。

但我试了四种候选写法去下单，**全部返回 success，且响应体完全一致——服务端不回显 modification**。

这意味着：**我无法从服务端确认特制到底生效了没有。**

工程取舍：采用语义最明确的 `{code, key: unselectedKey, quantity: 0}`，
并在预览卡片上明确标注"以门店出餐为准"。

这是本文里唯一一个**没有验证结论**的点，我不想假装它验证过了。
如果你有办法验证，欢迎提 Issue 告诉我。

## 五、微信侧的硬约束

公众号这一侧有三个绕不过去的约束，都来自官方一手文档：

**1. 5 秒不响应就断连，并重试 3 次**（同一条消息最多投递 4 次）。
来不及处理时的官方推荐做法是**回复 `success` 或空串**来抑制重试，同时按 **MsgId 去重**
（事件消息没有 MsgId，退化成 `FromUserName + CreateTime`）。

本项目的处理：

```
收到消息 → 4.3s 内跑完？ 是 → 被动回复 XML
                        否 → 回 success（抑制重试）+ 后台继续
                              ├ 有 AppSecret → 客服消息推回
                              └ 无 AppSecret → 存起来，用户下次发言时补上（30 分钟丢弃）
```

第二条分支不是凑数的——**个人订阅号没有客服消息接口权限**，
这条降级路径决定了这个项目在个人号上依然完整可用，只是体验打折。

**2. 客服消息有 48 小时交互窗口**（超窗报 45015）。
本项目的推送发生在用户发言后数秒内，天然在窗口内。但做延迟类功能前必须知道这条。

**3. 微信只回调 80/443 的公网 HTTPS。** 本地开发必须配内网穿透。

## 六、真钱之前的五道闸

`create-order` 会产生**真实订单和支付链接**。这不是"调用一个 API"，这是花钱。
所以这个项目的安全设计不是附加项，是主体：

1. **状态机**：`placed` 只能由 `confirming` 进入。让"未确认就下单"从"记得判断"变成"走不过去"。
2. **确认令牌**：HMAC-SHA256 绑定 `userId + 购物车指纹 + nonce + 过期时间`，一次性消费，5 分钟过期。
   刻意不做持久化——进程重启令牌立即失效，**失效方向是安全的**。
3. **守卫**：幂等（pending/succeeded/failed 三态）+ 冷却 + 每小时/每天次数 + 单笔/每日金额 + 401 冻结。
4. **失败是终态**：`create-order` 失败**绝不自动重试**。重复扣款远比让用户重发一次严重。
5. **401 立即冻结**一切写操作。

第 4 条值得单独说：大多数系统的直觉是"失败了重试一次"，但在支付场景这个直觉是反的。
**在钱的事情上，宁可让用户多操作一次，也不要让系统自作主张。**

## 七、零依赖的代价

整个项目零第三方依赖，用 Node 22 原生 `--experimental-strip-types` 直接跑 TypeScript。
好处是 clone 下来不用 `npm install`；代价是踩到两个 strip-only 模式的限制：

1. **不支持构造器参数属性**：`constructor(private readonly x: string)` 会报
   `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`。必须写成显式字段。
2. **类型不能当值导出**：`export { SomeType }` 在类型被剥离后会报
   "Export 'SomeType' is not defined in module"。

还有一个和 Node 无关但一样坑的：**Windows 上不要用 `new URL().pathname` 取目录**。
中文用户名会被百分号编码（`C:\Users\安` → `%E5%AE%89`），随后 `scandir` 直接 ENOENT。
用 `fileURLToPath()`。

## 八、可复用的经验

做完这一轮，如果要我再做一次 MCP 集成，会先做这三件事：

1. **写一个只读探针，把所有工具真实跑一遍，把响应存成快照。**
   文档会过时，快照不会。本项目 `src/data/sample.ts` 就是从真实探针快照生成的，
   所以离线演示里的 8 家门店、115 条菜单都是真的，不是手写的假数据。
2. **把"参数是否真的起作用"当成必测项。** `keyword` 不过滤、`searchType=1` 忽略关键词——
   这两个坑的共同点是：调用成功、返回 200、但参数被静默丢弃。**成功响应不等于参数生效。**
3. **涉及钱的调用，把安全写进类型和控制流，不要写在注释里。**
   注释会被绕过，状态机的迁移表不会。
